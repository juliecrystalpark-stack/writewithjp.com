Building a naming system players could actually recognize

The Problem

The client had dozens of promotional events, each with a title translated individually into English. On paper, each translation was accurate. In practice, none of it worked — players scanning a promotions screen couldn't tell a VIP-exclusive offer from a weekend bonus from a deposit reward, because every title was worded like a one-off, even when the underlying event type repeated constantly.

How I Approached It

I looked at it the way a player actually would: fast, scanning, deciding in half a second whether something's worth tapping. Nobody reads a promo screen top to bottom — they scan for a pattern that tells them what kind of thing they're looking at. If the first few words don't instantly communicate the event type, the player's already lost interest.

So instead of translating title by title, I built a small, fixed set of category labels — VIP Only, Time-Limited, Exclusive Offer, and a few others — mapped to the type of event underneath the wording, not the literal source phrase. Every VIP-only offer read as VIP Only, every time, regardless of how creative the original title got. Once a player learns what a label means once, they never have to re-learn it.

Along the way I also caught something the client hadn't flagged: one recurring reward was tied to a payment method that only exists in one region. Kept as-is, it would've shipped to a Western audience referencing something they couldn't use. I flagged it, and we swapped it for something market-agnostic before it went live.

The Result

The result was a more consistent promotional taxonomy designed to reduce recognition effort for players. Because the labels were built around event type rather than one-off phrasing, the team also gained a reusable system for future promotions instead of solving the same naming problem every time.

Retention · Social Casino

Push notification system, calibrated by urgency

Problem: Notification copy across every player trigger — reward reminders, expiring items, season-end warnings — sounded the same regardless of actual stakes, which trains players to ignore all of it.

Approach: Matched tone to real urgency trigger by trigger — playful for routine reminders, genuine urgency for time-sensitive ones — and audited the full set to cut repeated phrasing.

Result: Following rollout, the client reported stronger engagement and longer sessions. I did not have access to the underlying analytics, so I’m intentionally not attaching an unsupported percentage.

UI Strings · Social Casino

Mission copy — backend specs to player-facing lines

Problem: Mission names were written as technical specs — accurate for the dev team, unreadable at a glance for a player mid-session.

Approach: Rewrote each mission as a short, benefit-forward line, flagging ambiguous mechanics back to the client instead of guessing.

Result: One clarification surfaced a win condition the client's own team hadn't fully specified — the correction improved accuracy for players and internal QA alike.

Voice Systems · Social Casino

Seasonal character voice adaptation for an existing tutorial

Problem: An existing functional tutorial needed a seasonal variant — same mechanics, entirely different narrator personality.

Approach: Preserved every instructional beat exactly while rebuilding dialogue around a new voice, writing multiple takes per line to find where the persona could stretch without losing clarity.

Result: A reusable approach for adapting one tutorial across multiple character voices without touching the underlying game logic.
